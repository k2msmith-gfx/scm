# scm — plan

An R7RS-small Scheme in Rust: embeddable as a crate, runnable standalone,
with an LLVM-backed JIT and native AOT compilation on x86-64 Linux and
aarch64 macOS.

Status: **planning**. Nothing is built. This document is the argument for a
shape, not a schedule.

---

## 1. The requirements, and the two places they fight

As given:

1. Support R7RS-small.
2. Easy embedding in a Rust application, as a crate.
3. Native compilation on x86-64 Linux and aarch64 macOS.
4. Leverage LLVM — `inkwell` as the likely interface.
5. Run standalone.
6. Support JIT compilation.

Five of those compose. Two pairs do not, and both have to be resolved by
*architecture* rather than by effort:

**(2) vs (4): an LLVM dependency is not an easy dependency.** `llvm-sys`
needs a matching LLVM installation found via `llvm-config` at build time, and
inkwell pins one LLVM version per feature flag. A crate that drags that in
cannot be dropped into someone's `Cargo.toml` and built — which is most of
what "easy embedding" means. (It is also, specifically, the thing the
ray-steel evaluation scored as one of Steel's two real wins: a bare
`cargo build`, no Nix shell, no C compiler.)

→ **Resolution: LLVM lives behind a feature flag, off by default.** The
default build of the `scm` crate is pure Rust and compiles anywhere; `--features
jit` and `--features aot` pull in LLVM. This is not a compromise on (4), it is
the only way to have both, and it forces a clean IR boundary between the
front end and the backends, which we want regardless.

**(1) vs (6): full `call/cc` and native code pull in opposite directions.**
R7RS-small requires proper tail calls (§3.5, a *must*) and first-class,
multi-shot, re-entrant `call/cc` with `dynamic-wind`. Native code generated by
LLVM uses the C stack, which cannot be captured, copied, or re-entered. The
historical answers are all expensive: full CPS with a trampoline (Chicken),
stack copying with implementation-owned frame layouts (Chez), or quietly
shipping escape-only continuations and failing conformance (most embedded
Schemes, Steel included).

→ **Resolution: the VM's explicit stack stays the system of record, and the
JIT optimizes within frames rather than replacing the stack discipline.** See
§3. This is the single most important decision in the document and everything
downstream falls out of it.

### Non-goals (for now)

R7RS-large. Full numeric tower on day one (see §2.3). Threads and parallelism.
Windows. A debugger. Self-hosting. An FFI beyond what embedding needs.

## 2. What was verified before writing this

Three facts that are load-bearing and were checked rather than recalled.

### 2.1 inkwell is the right tool for IR and the wrong tool for the JIT

inkwell 0.10.0 (2026-08-06) supports LLVM 12.0 through 22.1 behind
per-version feature flags, so LLVM 21 is in range.

But its `ExecutionEngine` calls `LLVMLinkInMCJIT` — it is the **legacy MCJIT**
path, which LLVM has been deprecating for years in favour of ORCv2/LLJIT. The
only ORC code in inkwell is behind `#[cfg(feature = "experimental")]` and
targets the **ORCv1** C API (`LLVMOrcCreateInstance`,
`LLVMOrcAddLazilyCompiledIR`), which LLVM removed long ago.

Meanwhile `llvm-sys` — which inkwell sits on top of — exposes the modern API
in its `orc2` module (`LLVMOrcCreateNewThreadSafeContext`, LLJIT, and friends).

→ **Use inkwell for IR construction** (that is its real value: a safe,
typed builder API over `LLVMBuildXxx`) **and drop to `llvm-sys::orc2` directly
for the JIT.** Requirement (4) is satisfied; requirement (6) must not be built
on MCJIT. Expect to write and own a small safe wrapper over LLJIT — budget it
as real work, not glue.

### 2.2 The toolchain is already available and pinnable

`nixpkgs#llvmPackages.llvm` is **21.1.8**, matching inkwell's `llvm21-1`.
Host is aarch64 macOS 26.5.1. A flake pinning LLVM for both targets is the
right move and matches the existing `nix develop .#janet` pattern in ray —
with the difference that here the Nix shell is needed only for the
*LLVM-enabled* build, never for the default crate.

### 2.3 Bignums are optional, and that is a real scope lever

R7RS requires exact integers only "throughout the range of numbers permitted
as indexes of lists, vectors, bytevectors, and strings". Beyond that an
implementation "may report the violation of an implementation restriction".
Unbounded exact integers and exact rationals are advertised *optionally*,
through the `exact-closed` and `ratios` feature identifiers.

→ A conformant R7RS-small can ship with fixnums and flonums, declare neither
`exact-closed` nor `ratios`, and add bignums later without ever having been
non-conformant. `(features)` must be honest; that is the whole obligation.
This moves a large, fiddly chunk of work out of the critical path.

(Noted in passing: R7RS's own suggested architecture feature identifiers
include `llvm`.)

## 3. The spine: one explicit stack, three tiers above it

The hard problems — `call/cc`, proper tail calls, and GC roots in native code
— are all the same problem wearing different hats: *who knows where the live
values are?* Answer it once.

**The VM owns an explicit, heap-allocated frame stack. Native code borrows it;
it never replaces it.**

Consequences, all of them good:

- **`call/cc` is a data-structure operation.** Capturing a continuation copies
  (or, better, freezes and shares) a region of the explicit stack. Multi-shot
  and re-entrant come for free because nothing lives in C frames. No CPS
  conversion, no trampoline tax on every call.
- **Proper tail calls are trivial** — reuse the frame. No reliance on LLVM's
  `musttail`, whose guarantees vary by target and calling convention.
- **The GC root set is the explicit stack**, plus a small handle table for
  embedder-held values. No LLVM statepoints, no shadow-stack instrumentation,
  no conservative scanning of C frames, and therefore no barrier to a moving
  collector later.
- **The JIT cannot break semantics it never touches.** A JIT-compiled function
  reads and writes the same frames the interpreter does, so a continuation
  captured inside JIT'd code is captured from the same representation.

The price is honest and should be stated: **keeping frames in memory costs
straight-line speed**. LLVM will register-allocate *within* a frame and
optimize arithmetic, type checks, and inline caches, but it will not turn a
Scheme call into a native `call` with arguments in registers. That ceiling is
accepted deliberately in exchange for conformance, and it is the same bargain
Guile 3 made with its JIT.

The escape hatch, later and optionally: a region analysis that proves a
function (and everything it calls) cannot capture a continuation, and compiles
*that* region with a native calling convention. This is how the AOT tier
eventually gets fast. It is explicitly out of scope until the first three
tiers are correct and measured — but the IR should not make it impossible.

### Tiers

| tier | what | when |
|---|---|---|
| **T0** | AST interpreter over the explicit stack | first, and kept forever as the semantic oracle |
| **T1** | bytecode VM, same stack, same semantics | the default execution engine |
| **T2** | LLVM JIT of hot functions, via LLJIT, same stack | `--features jit` |
| **T3** | LLVM AOT to object files, linked into a standalone binary | `--features aot` |

T0 is not throwaway. It is the differential-testing reference for every tier
above it: *every* conformance test and benchmark runs on T0 and T1, and on T2
when enabled, and the three must agree. The ray-steel work is unambiguous
about where mechanical-translation bugs get caught — comparing against a
reference implementation on a number, not reading the diff.

### Crate layout

```
scm/              library: reader, expander, IR, GC, T0, T1, stdlib.  NO LLVM.
scm-llvm/         IR -> LLVM IR (inkwell), LLJIT (llvm-sys::orc2), AOT.
scm-cli/          the `scm` binary: REPL, script runner, `scm build`.
scm-conform/      the conformance runner and its vendored suites.
```

`scm`'s default features must stay LLVM-free forever. A CI job that builds it
with `--no-default-features` on a machine with no LLVM installed is the guard,
and it should exist from the first commit that has a `Cargo.toml`.

## 4. The front end, and the three things that are actually hard

Beyond the stack decision, three parts of R7RS-small are where
implementations go to die. Each deserves a design before it deserves code.

**Hygienic macros.** `syntax-rules` with nested ellipses, literals, and
correct hygiene is not a weekend. Recommendation: implement scopes as **sets
of scopes** (Flatt's model, as in Racket) rather than explicit renaming or
syntactic closures. It is the best-documented model, it handles the nasty
cases without special-casing, and it is the only one that extends cleanly to
procedural macros if we ever want them.

**The library system.** `define-library`, `import`, `export`, `include`,
`cond-expand`. This shapes how the global environment is represented, so it
cannot be bolted on after the compiler exists. It also determines whether the
stdlib can be precompiled — see §5.

**The numeric tower.** Fixnum/flonum first (§2.3), with the tagging and the
generic-arithmetic dispatch designed so bignums and ratios *slot in* rather
than requiring a rewrite. One carried lesson: in Steel, exactness propagation
silently turned a float integrator into bignum arithmetic, and nothing warned.
Whatever we do, exact/inexact transitions must be observable — a `(features)`
answer, a REPL warning, or a lint.

## 5. Startup time is a design requirement, not a tuning task

This repo exists one day after measuring Steel v0.8.3: **109 ms to run an
empty file, 61 ms of it `Engine::new`, with 0.8% of that executing Scheme and
~99% recompiling four `include_str!` constants that are fixed at build time.**
The cache that would have fixed it was written, commented out, and abandoned
because a static interner invalidated the image.

That is a trap to design out, not to discover. Therefore:

- The stdlib is **compiled at build time** into a serializable image, and boot
  is a deserialize. This constrains the library system (§4) and the interner:
  **no global/static interner state that the image cannot reconstruct.**
- **Boot budget: < 10 ms** for `scm -e '(values)'`, tracked in CI from the
  first release build, failing the build on regression.

Both platforms, both tiers. A JIT that takes 200 ms to warm up has not solved
startup; it has moved it.

## 6. Staging

Each stage has an exit criterion that is a measurement, not a feeling. Rough
sizes only — these are shapes of work, not estimates.

| | stage | exit criterion |
|---|---|---|
| **S0** | **LLVM feasibility spike.** inkwell + LLVM 21 + LLJIT via `llvm-sys::orc2`, building and running one JIT'd function, on aarch64-darwin *and* x86-64-linux. Throwaway code. | a JIT'd `fn(i64)->i64` returns the right answer on both targets, and `cargo build` of a stub `scm` with no LLVM present still works |
| **S1** | Reader, datum representation, writer, `(features)`. Fixnums/flonums. | read→write round-trip fuzzes clean on a corpus; `write`/`display` conform |
| **S2** | T0 interpreter: explicit stack, environments, closures, proper tail calls. | a tail loop of 10^8 iterations is flat in memory (measured, not asserted) |
| **S3** | GC: non-moving mark-sweep, roots = explicit stack + handle table. | cyclic structure is collected; GC stress test under a shrunk heap; no leak under `set!` cycles |
| **S4** | `syntax-rules`, the library system, `(scheme base)`. | the conformance number (§7) is reported for the first time |
| **S5** | `call/cc` (multi-shot), `dynamic-wind`, `guard`/exceptions, `values`, `parameterize`, promises. | multi-shot re-entry tests pass; `dynamic-wind` ordering tests pass |
| **S6** | The rest of R7RS-small: chars/strings/Unicode, ports, bytevectors, `eval`. | conformance ≥ 95% with every failure individually explained |
| **S7** | **Embedding API.** Safe `Value` handles, rooting, host-function registration, error propagation as `Result`. | a sample Rust app embeds scm in < 30 lines; no panic crosses the API under a fuzzed host-call harness |
| **S8** | Precompiled stdlib image; boot budget met. | `scm -e '(values)'` < 10 ms, in CI |
| **S9** | T1 bytecode VM. | benchmark suite vs T0, and T0/T1 agree on every conformance test |
| **S10** | T2 JIT (`--features jit`). | measured speedup over T1 on the benchmark suite; T1/T2 agree on every conformance test; `call/cc` captured inside JIT'd code still works |
| **S11** | T3 AOT + `scm build` producing a native binary. | a hello-world binary runs on both targets with no toolchain present at runtime |

The ordering is deliberate: **S7 and S8 come before the JIT.** Embedding and
startup are requirements (2) and the thing that makes (5) pleasant; the JIT is
a performance feature that cannot be evaluated until there is something
correct to compare it against. If the schedule slips, it slips at S10/S11, and
what ships is a conformant, embeddable, fast-booting interpreter — which is a
useful artifact on its own.

## 7. How "supports R7RS-small" becomes a number

Conformance is not an opinion. From S4 onward, CI reports a percentage against
vendored external suites, and the number goes in the README:

- **`r7rs-tests.scm`** (the Chibi-Scheme / Larceny suite) as the primary
  oracle. Written by other people, against the spec, with no knowledge of our
  implementation.
- **The R7RS benchmark suite** (~44 programs: `ack`, `nboyer`, `fft`,
  `nucleic`, `earley`, …) for performance *and* as a second correctness
  corpus. Already a known quantity — Steel's tree carries it.
- Our own tests for everything the external suites miss.

Two rules, both earned the hard way:

1. **Every tier runs every test.** A JIT that passes fewer tests than the
   interpreter is a bug, not a tradeoff.
2. **A failing test is either fixed or individually explained in a file.** A
   conformance percentage with an unexplained remainder is a marketing number.

Performance gets the same treatment: a committed baseline JSON, a table script
that diffs a run against it, and a profile — the Steel session's harness is
the pattern, and it took an afternoon.

## 8. Risks, worst first

1. **The JIT's ceiling.** Keeping frames in memory (§3) caps how fast T2 can
   be. It is possible that T2 beats T1 by 2x where a conventional native
   compiler would beat it by 10x, and that this is judged not worth the LLVM
   dependency. *Mitigation: S0 and S10 are cheap to reach relative to the
   whole, and the region analysis escape hatch exists. But this is the bet.*
2. **LLVM as a dependency.** Version churn across LLVM 21→22→23, inkwell's
   per-version feature flags, `llvm-config` discovery, and a multi-GB
   toolchain. *Mitigation: pinned via flake; LLVM off by default; the
   `--no-default-features` CI job.*
3. **macOS arm64 JIT specifics.** W^X enforcement means `MAP_JIT` plus
   `pthread_jit_write_protect_np` toggling, and the hardened runtime wants the
   `com.apple.security.cs.allow-jit` entitlement. This has bitten every JIT on
   Apple Silicon. *Mitigation: it is the explicit subject of S0, on real
   hardware, before anything depends on it.*
4. **R7RS-small is bigger than it reads.** Hygiene, the library system, the
   numeric tower, Unicode, and ports are each weeks. *Mitigation: the
   conformance number makes progress visible from S4, and §2.3 legitimately
   removes bignums from the critical path.*
5. **GC correctness.** Collector bugs are nondeterministic and awful.
   *Mitigation: roots are one explicit structure (§3), and a shrunk-heap
   stress mode runs in CI from S3.*

## 9. Prior art worth reading before writing

- **Chez Scheme** — the reference for fast native code *with* real `call/cc`
  (stack segments). Read this before finalizing §3.
- **Guile 3** — a bytecode VM with a JIT that keeps the VM stack. The closest
  precedent for the tier design here.
- **Chicken** — CPS and Cheney-on-the-MTA: the road not taken, and why.
- **Chibi-Scheme** — small, readable, R7RS-complete, and the source of the
  conformance suite.
- **Racket** — sets of scopes (§4).
- **Extempore** — an existing LLVM-JIT Scheme-family language; the precedent
  that requirement (6) is achievable at all.
- **Steel** — Rust embedding patterns, and a measured catalogue of what to
  avoid (startup, stdlib holes, 292 `unsafe` occurrences in 97.6k lines).

## 10. Open questions

1. **Who is the first consumer?** If scm is eventually ray's and the modeler's
   scripting layer, then S7 (embedding) and S8 (boot) are the *point* and
   should be pulled even earlier, the API shape should be designed against
   ray's ~6,200-line prelude, and "a runtime that cannot abort the host" joins
   the requirements. If scm is a language project in its own right,
   conformance and S10/S11 lead. The plan above hedges; saying which would
   sharpen it.
2. **Does `call/cc` have to be multi-shot?** R7RS-small says yes, and §3 is
   designed around it. Escape-only continuations would be substantially
   cheaper and would permit a conventional native calling convention — at the
   cost of conformance. Worth saying out loud once, then never revisiting.
3. **Run S0 now?** It is the only stage whose failure invalidates the plan, it
   needs a multi-GB LLVM fetch, and it is a day or two of throwaway code.
